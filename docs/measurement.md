# 10만 건 실측

워커 3개로 10만 건을 전량 발송하고 진행률을 30초 간격으로 기록했습니다. 요약은 [README의 실측 섹션](../README.md#실측)에 있고, 이 문서는 측정 방법과 구간별 데이터, 그리고 원인을 좁혀간 과정을 담습니다.

## 측정 방법

```bash
docker compose up -d --build --scale worker=3
```

알림을 생성하고 발송을 시작한 뒤, 단건 조회 API를 30초마다 호출해 `status`와 상태별 건수를 기록했습니다.

```bash
while :; do
  curl -s localhost:3000/api/v1/alarms/$ALARM_ID \
    | jq -r '[(now|floor), .data.status, .data.progress.pending, .data.progress.inFlight,
              .data.progress.sent, .data.progress.failed, .data.progress.unknown] | @csv'
  sleep 30
done
```

설정은 기본값을 그대로 썼습니다 — `RATE_LIMIT_PER_SEC=45`, `MAX_IN_FLIGHT=100`, `CLAIM_BATCH_SIZE=50`, `SEND_TIMEOUT_MS=5000`, `MAX_ATTEMPTS=5`.

## 결과

| 항목 | 값 |
| --- | --- |
| 대상 | 100,000 |
| `sent` | 99,001 |
| `failed` | 999 |
| `unknown` | 0 |
| 안정 구간 처리량 | 26~27.6/s |
| 동시 발송 건수 | 평균 20.8, 최대 76 (상한 300) |

재시도 분포와 회수 횟수는 종료 후 DB에서 직접 확인했습니다.

| `attempts` | 건수 |
| --- | --- |
| 1 | 94,940 |
| 2 | 4,792 |
| 3 | 259 |
| 4 | 8 |
| 5 | 1 |

2회 이상 시도된 건이 5,060건(5.1%)으로 발송 API의 5xx 비율과 일치합니다. `recovery_count`는 전 행이 0이었습니다 — lease 만료로 회수된 건이 없었다는 뜻입니다.

## 총 소요시간을 인용하지 않는 이유

`startedAt`부터 `finishedAt`까지는 127.8분이었지만 이 값은 쓰지 않았습니다. 측정 중 호스트가 스로틀링되어 **발송 속도가 아닌 것이 섞여** 있기 때문입니다.

10분 단위로 묶으면 50분 지점에서 절벽이 보입니다.

| 구간 | 처리량 | `sent` 증가 |
| --- | --- | --- |
| 0~10분 | 27.2/s | +15,526 |
| 10~20분 | 26.3/s | +15,785 |
| 20~30분 | 26.1/s | +15,665 |
| 30~40분 | 27.4/s | +16,452 |
| 40~50분 | 27.6/s | +16,613 |
| 60~70분 | 4.0/s | +4,286 |
| 80~90분 | 2.9/s | +3,308 |
| 100~110분 | 4.7/s | +6,686 |
| 120~130분 | 2.7/s | +2,743 |

50~60, 70~80, 90~100, 110~120분 구간에는 **기록이 한 줄도 없습니다.** 모니터링 요청이 10분 넘게 응답을 받지 못했다는 뜻이고, 그 API는 DB 조회만 합니다.

DB는 정상이었습니다.

| 지표 | 값 | 해석 |
| --- | --- | --- |
| 슬로우 쿼리(1초 초과) | 1건 | 클레임·결과 기록은 끝까지 빨랐음 |
| `alarm_deliveries` 죽은 튜플 | 19,847 / autovacuum 10회 | 블로트를 따라잡고 있었음 |
| `alarms` 갱신 횟수 | 2,141 | 집계가 배치 단위로 묶여 단일 행 경합이 없었음 |
| `recovery_count` | 전 행 0 | lease 만료 회수가 발생하지 않았음 |

결정적인 건 지연과 처리량의 비율입니다. 느린 구간은 동시 발송 건수 5~9에 처리량 3/s로 평균 지연 약 1.7초, 안정 구간은 25에 27/s로 약 0.9초였습니다. **지연은 2배만 늘었는데 처리량은 9배 떨어졌습니다.** 외부 응답을 기다린 것이 아니라 워커가 요청을 띄우지 못한 것이고, 그때 발송 대기 중인 건이 1만 8천 건 남아 있었습니다.

워커 3개와 API가 동시에 느려졌는데 DB만 정상이라면 남는 설명은 그 프로세스들이 올라가 있는 호스트입니다. 측정을 노트북에서 돌리고 자리를 비운 시점과 절벽이 일치합니다.

재측정할 때는 전원을 연결하고 절전을 막아야 합니다.

```bash
caffeinate -is
```

## 처리량이 한도의 60%에 머문 이유

안정 구간의 26~27.6/s는 호스트와 무관한 값입니다. 설정 한도는 45/s인데 60% 수준입니다. 후보를 하나씩 배제했습니다.

**처리량 제한 — 아님.** Lua 스크립트는 `prev * (1 - ratio) + cur >= limit`으로 판정합니다. 균일하게 초당 R건이 나가는 정상 상태에서 이 식은 `R*(1-ratio) + R*ratio = R`로 R에 수렴하므로, R이 한도 미만이면 거부가 발생하지 않습니다. 27/s에서는 리미터가 작동조차 하지 않습니다.

**동시성 상한 — 아님.** 동시 발송 건수는 최대 76이었고 상한은 워커 3개 합산 300입니다. 한 번도 포화되지 않았습니다.

**클레임 배치의 경계 — 이것입니다.** 동시 발송 건수가 7과 76 사이를 반복해 오갔습니다. 배치를 클레임해 한꺼번에 투입하면 급등하고, 꼬리에 남은 느린 건(타임아웃 5초)을 기다리는 동안 7까지 비는 패턴입니다.

`DeliveryDispatcher`는 레인 수를 `min(MAX_IN_FLIGHT, batch.length)`로 잡습니다. `CLAIM_BATCH_SIZE`(50)가 `MAX_IN_FLIGHT`(100)보다 작으면 모든 건이 각자 레인을 받아, 의도한 동시성 풀이 배치 단위 `Promise.all`과 같아집니다. 배치 50건에 타임아웃 확률 2%면 배치의 64%가 이 영향을 받습니다.

리틀의 법칙으로 교차검증됩니다. 평균 동시 발송 20.8, 지연 0.9초면 처리량은 약 23/s입니다. 한도 45/s를 채우려면 동시 발송을 40 이상으로 **지속** 유지해야 합니다.

워커 증설로는 해결되지 않습니다. 각 워커가 자기 배치의 꼬리를 기다리므로 유휴 구간도 함께 복제됩니다.

## 측정에서 배운 것

**관측 지점을 두 번 잘못 잡았습니다.**

처음에는 배치 경계가 있으면 처리량 그래프가 톱니로 보일 것이라 예상했습니다. 그런데 워커 3개의 배치 위상이 서로 어긋나고 30초 샘플이 여러 배치를 덮어, **처리량은 평평해지고 요동은 동시 발송 건수에만 남았습니다.** 처리량만 보면 구조적 상한으로 오판합니다.

두 번째로, 샘플을 10행마다 출력해 추이를 보다가 50분 지점의 절벽을 놓쳤습니다. 출력된 지점들이 우연히 모두 정상 구간이었고, 전체 평균(13.1/s)과 구간 값(27/s)이 모순되는 것으로만 드러났습니다. 결론을 내기 전에 전체 구간을 빠짐없이 묶어봐야 합니다.
